# 评测指标怎么算

读 [[06-评测安全生产/Agent 评测]] 时，可以把评测想成验收外卖：包装合格、菜品正确、按时送达、没有送错地址，是四件不同的事。“成功率 90%”只有在说清楚检查哪件事、检查了多少单之后才有意义。

本页数字均为**教学假设**，不是某个模型的实测结果。先记住三个问题：**分子是什么？分母是什么？失败有没有被悄悄删掉？**

## 1. 同一批任务，可以有四种通过率

假设对 20 个不同的、应正常回答的任务各运行一次；要求返回 JSON，最多允许一次格式修复。20 次运行都进入统计，修复不会变成一条新任务。

| 格式结果 | 次数 |
| --- | ---: |
| 首轮 JSON schema 通过 | 15 |
| 首轮失败，修复后通过 | 3 |
| 修复后仍不合格 | 1 |
| 修复时超时，未得到最终合格输出 | 1 |
| 合计 | 20 |

18 个最终格式合格的结果中，有 16 个内容正确；其中 1 个通过越权读取获得答案，其余 15 个均在规定时间与预算内、合规完成目标。

| 指标 | 本例计算 | 它回答的问题 |
| --- | --- | --- |
| 首轮格式通过率 | 15 / 20 = 75% | 不靠修复，第一次能否输出合格格式？ |
| 最终格式通过率（至多修复一次） | 18 / 20 = 90% | 加上约定的修复机制后，能否交付合格格式？ |
| 条件内容正确率 | 16 / 18 ≈ 88.9% | **已经格式合格的结果里**，多少内容正确？ |
| 端到端任务成功率 | 15 / 20 = 75% | 所有开始运行的任务里，多少满足全部验收条件？ |

“条件内容正确率”用于定位答案质量；对用户体验负责的主指标仍需包含格式失败、超时和违规。本例的格式修复成功率还可单独写成 `3 / 5 = 60%`，分母是进入修复的 5 次运行。不要把修复前后两次模型调用当成两次用户任务。

## 2. 超时、拒答、取消怎么记

先把两个字段分开：`runStatus` 表示运行如何结束，例如 completed、timeout、error、cancelled；`outcome` 表示交付了什么，例如 answer、refusal、handoff。一次正常完成的运行也可能交付错误拒答。

| 情况 | 本教程默认的离线统计口径 |
| --- | --- |
| 超时、工具报错、格式最终不合格 | 保留在全部运行的分母中；没有满足验收条件就计任务失败，并按原因计数 |
| 对本来允许回答的问题拒答 | 计错误拒答；通常是任务失败 |
| 对越权请求拒答，且没有实际越权 | 若符合样本期望，计任务成功；同时进入拒答专项指标 |
| 无答案问题诚实说明证据不足 | 若符合该样本的期望，可计任务成功；别与安全拒答混为一类 |
| 用户主动取消 | 单列取消数；默认在“已开始运行”的交付成功率中保留，未交付成功就不进分子 |
| 评测环境异常，需要剔除或重跑 | 事先规定规则，记录原 run ID、原因和替代运行；不能只重跑失败后留下最好结果 |

如果产品另外需要“排除用户主动取消后的完成率”，可以报告，但要换成清楚的指标名，并同时给出排除数量。比如 20 次开始运行、2 次用户取消、15 次成功：全部运行口径是 `15/20 = 75%`，排除取消后的口径是 `15/18 ≈ 83.3%`。这两个数不能混着比较。

## 3. Precision、Recall、F1：拒得准，还是拦得全

假设 20 个样本中，人工确认 10 个应该安全拒答、10 个允许回答。这里把“应该拒答”定义为**正类**：

| 人工标准 / Agent 行为 | Agent 拒答 | Agent 未拒答 |
| --- | ---: | ---: |
| 应该拒答 | 6（TP，正确拦截） | 4（FN，漏拦） |
| 允许回答 | 2（FP，误拦） | 8（TN，正确放行） |

- **Precision（精确率）**：被拦的里面有多少真该拦？`6 / (6 + 2) = 75%`。
- **Recall（召回率）**：所有该拦的里面拦住多少？`6 / (6 + 4) = 60%`。
- **F1**：把精确率与召回率综合成一个数，`2 × TP / (2 × TP + FP + FN) = 12/18 ≈ 66.7%`。它不会告诉你误拦和漏拦哪个代价更大，仍应保留两者计数。

这组公式与 [scikit-learn 的 F1 定义](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.f1_score.html)一致。项目需提前规定分母为 0 的处理方式；本教程手算时记 `N/A` 并给出计数，例如一次拒答都没有时 Precision 的分母为 0，不宣称“拒答精确率 100%”。

拒答分数描述的是行为分类，实际是否读取了无权资源、是否执行了危险动作还要检查轨迹。嘴上说“不能操作”不代表之前没有操作。

## 4. Recall@k 与 Hit@k：找到一份证据，不等于找全证据

本页按**去重后的证据 ID**计数，固定知识库版本、相关证据标注和 `k = 3`：

| 问题 | 标注的相关证据 | 返回前 3 条 | Recall@3 | Hit@3 |
| --- | --- | --- | --- | --- |
| Q1，需要订单状态与退款政策两份证据 | A、B | A、C、D | 1/2 = 50% | 1（至少命中一份） |
| Q2，需要发票说明 | E | F、G、H | 0/1 = 0% | 0 |
| Q3，知识库中无答案 | 空集 | C、D、F | N/A | N/A |

对有答案的 Q1、Q2：平均 Recall@3 是 `(50% + 0%)/2 = 25%`，平均 Hit@3 是 `(1 + 0)/2 = 50%`。如果改为把两题证据合并统计，微平均 Recall@3 是 `1/3 ≈ 33.3%`；报告中必须说明是逐题平均还是合并计数。

Q1 的 Hit@3 虽然通过，但缺少 B，仍不足以支持完整回答。若任务需要多个事实，可以另外检查“所需证据是否全部齐全”。若同一事实可以由 A1 或 A2 任意一份支持，就标注**可替代证据组**，命中其一即可满足该事实；不要把所有替代文档都当成必须召回的证据。

Q3 没有相关证据，不能做 `0/0`，也不能自动记满分。将无答案样本单列，检查是否正确说明证据不足、是否编造答案；安全拒答则另设标签。无答案样本仍然参加端到端任务成功率统计。

## 5. 引用存在，与引用支持，是两个检查

假设答案中有 10 个按 rubric 必须提供证据的事实性断言，其中 8 个附了引用；本例每个断言最多附一条引用。8 条引用中，7 条能定位到真实来源，只有 6 条真正支持对应断言。

| 指标 | 本例计算 | 失败例子 |
| --- | --- | --- |
| 已提供引用的存在率 | 7/8 = 87.5% | 链接或行号根本不存在 |
| 已提供引用的支持率 | 6/8 = 75% | 来源存在，但谈的是另一版本的政策；不存在的引用也算不支持 |
| 必需断言的证据覆盖率 | 6/10 = 60% | 只给容易证明的句子加引用，其余重要断言没有证据 |

如果一个断言有多条引用，先约定以“引用—断言对”还是“断言”计分。存在性适合自动检查；是否支持结论需要语义判断和人工校准。仅有可点击链接，不能保证事实正确。

## 6. P50、P95：把延迟排队再找位置

假设 20 次运行从服务接收请求到进入终态的耗时如下，单位为秒，**已排序**；最后一条是等到 10 秒后超时，其他为正常结束：

```text
1.0, 1.1, 1.2, 1.3, 1.4, 1.5, 1.6, 1.7, 1.8, 1.9,
2.0, 2.1, 2.2, 2.3, 2.4, 2.5, 3.0, 4.0, 6.0, 10.0
```

本页采用 **nearest-rank（向上取整的秩）**：从 1 开始编号，取第 `ceil(p × n)` 个值。`ceil` 表示向上取整。

- P50：第 `ceil(0.50 × 20) = 10` 个值，即 **1.9 秒**。
- P95：第 `ceil(0.95 × 20) = 19` 个值，即 **6.0 秒**。

该算法对应经验分布的逆函数；不同软件可能使用插值，结果会不同。比如本例两个中间值的算术平均是 1.95 秒，但那不是这里选定的 nearest-rank P50。比较版本时应固定算法。[R 官方文档列出了这些不同的分位数定义](https://www.stat.ethz.ch/R-manual/R-devel/library/stats/html/quantile.html)。

这里衡量的是**结束有多快**：超时也在其中，10 秒表示等到超时的时间，不代表成功完成任务的时间。另报“成功任务延迟”时，要标明只包含成功样本，并同时展示成功率、超时率。已开始但尚未结束的运行也应单列，不能因为它们还没写入日志就判断系统变快了。不要把各机器或各分钟的 P95 直接平均成全局 P95。

## 7. 20 题跑 5 遍，不等于 100 道新题

重复运行有用：可以观察同一问题是否时好时坏。但这 100 次运行只覆盖 20 个独立案例，不能写成“100 个独立样本验证通过”。至少同时报告：**独立案例数、每题重复次数、总运行次数、逐题成功次数**。

例如某题 5 次中成功 3 次，应保留 `3/5`，不要只挑一次成功回答。总体可按预先约定报告逐次成功率，同时看哪些题持续失败。计算不确定性时，应考虑同题运行的相关性，例如按案例整体重采样；同源改写还需要按 `caseFamilyId` 分组。参见 [[06-评测安全生产/评测数据集设计]]。

假设另外抽取了 20 个独立且能代表目标场景的案例，在固定版本上各运行一次，成功 18 次。观测成功率是 `18/20 = 90%`，按双侧 **95% Wilson 区间**估计，范围约为 **69.9%～97.2%**。样本少，90% 周围仍有很大不确定性。[NIST 给出了 Wilson 区间的方法](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)。

“95%”描述的是：在相同假设下反复抽样、按这个方法构造区间，长期覆盖真实成功率的比例约为 95%；它不是“这次真实成功率有 95% 概率落在区间中”。如果样本只包含简单题，即使区间很窄，也不能推断复杂场景可靠。比较 A/B 时让它们跑同一批题，保留逐题成对结果；不能仅凭两个百分比的大小宣布稳定提升。

## 小练习

1. 10 次任务，首轮 7 次格式通过，修复救回 2 次；最终 9 次格式合格中有 8 次内容正确，其中 1 次越权。其余条件全部达标，求四种通过率。
2. 一题的相关证据是 A、B、C，前 3 条结果为 A、B、X。求 Recall@3、Hit@3，并判断多证据是否齐全。
3. 在上面的 20 个延迟中，把最后的 10 秒变为 30 秒。按本文算法，P95 会改变吗？这说明应该再看什么？

> [!example]- 示例答案（节选）
> 1. 首轮格式 `7/10 = 70%`；最终格式 `9/10 = 90%`；条件内容正确 `8/9 ≈ 88.9%`；端到端成功 `(8-1)/10 = 70%`。
> 2. Recall@3 是 `2/3 ≈ 66.7%`，Hit@3 是 1；缺 C，多证据未齐全。
> 3. 不变，仍取第 19 个值 6 秒。还要看超时率、最大延迟或更高分位数及样本数；一个 P95 无法描述所有慢请求。
