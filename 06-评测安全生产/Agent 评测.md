# Agent 评测

## 为什么不能只看最终回答

Agent 是多步系统。最终失败可能来自任务理解、检索、工具选择、参数、工具执行、状态更新或答案合成。评测必须能定位具体阶段。

## 三层评测

1. **组件层**：Prompt schema、检索、单个工具、权限规则。
2. **轨迹层**：工具选择是否正确、步骤是否冗余、是否违反约束。
3. **任务层**：最终结果是否正确、完整、及时且成本可接受。

## 最小数据集字段

```yaml
id: order-status-001
input: 查询订单 A123 的当前状态
expected_outcome: 返回源系统状态并标注查询时间
allowed_tools: [get_order_status]
forbidden_actions: [update_order]
rubric: [事实正确, 无越权, 有来源]
```

## 指标

先为每个指标写清楚分母、统计窗口、成功条件和是否包含超时。具体手算见 [[06-评测安全生产/评测指标怎么算]]。

| 指标 | 建议口径 |
| --- | --- |
| 端到端任务成功率 | 满足该样本全部验收条件的 run 数 / 全部纳入评测的 run 数；修复和重试留在原 run 内 |
| 格式与内容 | 分别报告首轮格式通过率、约定修复次数内的最终格式通过率，以及格式合格结果中的条件内容正确率 |
| 拒答质量 | 定义“应该拒答”为正类，分别统计拒答 Precision、Recall 和误拒答数量；无答案场景另设标签 |
| 工具选择、参数正确率 | 在人工标注的工具决策点上评估工具选择（含应调用却未调用）；参数通过次数 / 实际发起的工具调用次数另报 |
| 步骤与重复调用 | 按 run 报告步骤分布；重复调用次数 / 全部工具调用次数，并预先规定什么算无必要的重复 |
| 延迟与成本 | 分别报告全部终态 run、成功 run 的 P50/P95、样本数，以及每个开始运行的任务成本；说明是否包含排队和审批等待 |
| 安全与人工介入 | 有安全违规的 run 数 / 全部评测 run 数，并保留严重违规事件数；人工接管 run 数 / 全部评测 run 数 |

不同项目可以采用不同口径，但基线与候选版本必须一致。高风险子集单独报告，避免大量简单查询稀释越权或写操作失败。

## 回归流程

线上失败脱敏后进入候选集 → 人工确认期望结果 → 固定模型/Prompt/工具版本运行 → 与基线比较 → 达标后发布。

## 先定义任务，再定义分数

“回答质量好”无法作为发布门禁。把目标拆成可观察标准：事实正确、引用支持、完成用户目标、没有越权、在预算内结束。不同任务使用不同权重，高风险任务可以规定任何安全违规都直接失败。

## 确定性评分与模型评分

优先使用确定性评分：JSON schema、精确字段、工具轨迹、引用存在性、权限规则、编译/测试结果。只有语言质量、语义完整性等难以规则化的维度才使用人工或 LLM-as-a-judge。引用存在只能证明找得到来源；“来源是否支持断言”还要另评，并检查重要断言是否漏引。

## LLM-as-a-judge 的边界

- 给出明确 rubric 和离散分值定义。
- Judge 不应看到候选版本名称，减少偏见。
- 对少量数据由多名人工标注，校准 Judge 与人工一致性。
- 固定 Judge 模型和 Prompt 版本。
- 不让同一模型的单次自评成为唯一质量证据。

## 轨迹评分

最终答案正确也可能通过危险路径得到。例如 Agent 读取了无权数据但没有展示。轨迹评测应检查：允许/禁止工具、调用顺序、参数来源、重复动作、是否跳过审批、关键观察是否被使用。

> [!example]- 帮助理解：最终回答相同，得分为什么不同
> 三个 Agent 最终都回答“订单 A123 已发货”：
>
> | 运行 | 得到答案的方式 | 文本事实 | 轨迹/证据层 | 安全层 | 端到端任务 |
> | --- | --- | --- | --- | --- | --- |
> | A | 调用允许的订单工具并引用查询时间 | 正确 | 通过 | 通过 | 通过 |
> | B | 没有查询，只是碰巧猜对 | 碰巧正确 | 失败 | 通过 | 失败 |
> | C | 读取无权访问的后台表得到正确状态 | 正确 | 失败 | 硬门禁失败 | 失败 |
>
> 假设三次运行都已纳入评测，且其他条件都达标：文本事实正确是 `3/3`，端到端任务成功却是 `1/3`。C 即使没有把私密字段展示出来，也已经发生越权访问。

## Pairwise 与 Pointwise

- Pointwise：按固定 rubric 给单个结果评分，适合门禁。
- Pairwise：比较 A/B 哪个更好，适合 Prompt 或模型迭代。

Pairwise 需要交换展示顺序，防止位置偏差；“更好”仍应拆成具体维度。

## 统计注意

小样本的 90% → 95% 可能只是随机波动。报告独立案例数、每题运行次数、置信区间和分类型结果，特别关注严重失败数量。20 题各跑 5 遍可以衡量稳定性，但不是 100 道独立新题。平均分可能掩盖某个关键场景完全不可用。参见 [[06-评测安全生产/评测指标怎么算]] 的 20 题 Wilson 区间算例。

## 发布门禁示例

以下阈值仅演示如何把目标写成规则，**不是各类 Agent 通用的发布标准**。实际值应结合风险、基线、样本量和产品预算预先确定；测试集上“发现 0 次违规”也不能证明真实违规概率为 0。

```yaml
overall_task_success: ">= 0.90"
safety_violation_count: 0
write_without_approval: 0
provided_citation_support_rate: ">= 0.95"
required_claim_evidence_coverage: ">= 0.95"
p95_latency_seconds: "<= 8"
cost_increase_vs_baseline: "<= 15%"
critical_regressions: 0
```

其中引用支持率按已提供的“引用—断言对”计算，证据覆盖率按需证据的断言计算；延迟包含排队和修复，统计到终态，并单列超时率。把数据集/版本、分位数算法、样本数、允许修复次数一起写入报告，阈值才可复现。

## 在线评测

离线评测通过后，先 shadow/canary。线上关注用户纠正、人工接管、工具失败、拒绝率、成本和延迟。用户点赞不能单独代表事实正确。
