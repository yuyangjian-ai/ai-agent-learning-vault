# Agent 评测

## 为什么不能只看最终回答

Agent 是多步系统。最终失败可能来自任务理解、检索、工具选择、参数、工具执行、状态更新或答案合成。评测必须能定位具体阶段。

## 三层评测

1. **组件层**：Prompt schema、检索、单个工具、权限规则。
2. **轨迹层**：工具选择是否正确、步骤是否冗余、是否违反约束。
3. **任务层**：最终结果是否正确、完整、及时且成本可接受。

## 最小数据集字段

```yaml
id: order-status-001
input: 查询订单 A123 的当前状态
expected_outcome: 返回源系统状态并标注查询时间
allowed_tools: [get_order_status]
forbidden_actions: [update_order]
rubric: [事实正确, 无越权, 有来源]
```

## 指标

- 任务成功率、拒答准确率
- 正确工具选择率、参数正确率
- 平均步骤数、重复调用率
- P50/P95 延迟、token 和成本
- 安全违规率、人工介入率

## 回归流程

线上失败脱敏后进入候选集 → 人工确认期望结果 → 固定模型/Prompt/工具版本运行 → 与基线比较 → 达标后发布。

## 先定义任务，再定义分数

“回答质量好”无法作为发布门禁。把目标拆成可观察标准：事实正确、引用支持、完成用户目标、没有越权、在预算内结束。不同任务使用不同权重，高风险任务可以规定任何安全违规都直接失败。

## 确定性评分与模型评分

优先使用确定性评分：JSON schema、精确字段、工具轨迹、引用存在性、权限规则、编译/测试结果。只有语言质量、语义完整性等难以规则化的维度才使用人工或 LLM-as-a-judge。

## LLM-as-a-judge 的边界

- 给出明确 rubric 和离散分值定义。
- Judge 不应看到候选版本名称，减少偏见。
- 对少量数据由多名人工标注，校准 Judge 与人工一致性。
- 固定 Judge 模型和 Prompt 版本。
- 不让同一模型的单次自评成为唯一质量证据。

## 轨迹评分

最终答案正确也可能通过危险路径得到。例如 Agent 读取了无权数据但没有展示。轨迹评测应检查：允许/禁止工具、调用顺序、参数来源、重复动作、是否跳过审批、关键观察是否被使用。

## Pairwise 与 Pointwise

- Pointwise：按固定 rubric 给单个结果评分，适合门禁。
- Pairwise：比较 A/B 哪个更好，适合 Prompt 或模型迭代。

Pairwise 需要交换展示顺序，防止位置偏差；“更好”仍应拆成具体维度。

## 统计注意

小样本的 90% → 95% 可能只是随机波动。报告样本数、置信区间和分类型结果，特别关注严重失败数量。平均分可能掩盖某个关键场景完全不可用。

## 发布门禁示例

```yaml
overall_task_success: ">= 0.90"
safety_violation_count: 0
write_without_approval: 0
citation_support_rate: ">= 0.95"
p95_latency_seconds: "<= 8"
cost_increase_vs_baseline: "<= 15%"
critical_regressions: 0
```

## 在线评测

离线评测通过后，先 shadow/canary。线上关注用户纠正、人工接管、工具失败、拒绝率、成本和延迟。用户点赞不能单独代表事实正确。
