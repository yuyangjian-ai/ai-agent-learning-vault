# 可观测性与生产化

## 一次 run 要能回答

- 用户目标是什么，使用了哪个模型和 Prompt 版本？
- 每一步为什么调用这个工具，输入输出是什么？
- 花了多少时间、token 和费用？
- 最终状态是什么，失败发生在哪一层？
- 是否经过审批，谁批准了什么动作？

## 关键遥测

| 类型 | 示例 |
| --- | --- |
| Trace | model call、tool call、retrieval、approval |
| Metrics | 成功率、P95 延迟、成本、循环步数、拒答率 |
| Logs | 结构化错误、run ID、版本、脱敏摘要 |
| Audit | 身份、资源、动作、策略结果、确认记录 |

## 上线检查

- [ ] 模型/Prompt/工具 schema 有版本号和回滚方案。
- [ ] 限流、超时、熔断、重试和降级已定义。
- [ ] 预算同时限制单 run、单用户和全局额度。
- [ ] 长任务支持取消、断点恢复或幂等重跑。
- [ ] 敏感数据有分类、脱敏和保留策略。
- [ ] 评测门禁和灰度发布已接入。
- [ ] 人工接管时能看到完整但合规的上下文。

## 优先告警

安全违规、写工具失败、成本突增、循环耗尽、无答案率突变、特定模型版本质量下降。

## Trace 层次

```text
agent.run
  context.build
    memory.retrieve
    rag.retrieve
  model.call
  tool.call
    policy.check
    external.request
  approval.wait
  model.call
  response.validate
```

每个 span 带 `runId/stepId`、逻辑模型、Prompt/工具版本、状态和耗时。高基数字段如完整参数不适合作为 metrics label；敏感内容默认不进入 span attributes。

> [!example]- 帮助理解：从 P95 告警定位真正的慢点
> | Span | 耗时 | 结果 |
> | --- | --- | --- |
> | `context.build` | 120 ms | 成功 |
> | `model.call` | 650 ms | 成功 |
> | `order.tool` 第一次 | 5,000 ms | 超时 |
> | `order.tool` 重试 | 5,000 ms | 超时 |
> | `response.validate` | 30 ms | 降级回答 |
>
> 端到端约 10.8 秒，但根因不是“模型太慢”，而是订单工具连续超时。立即止损可以是熔断该工具并返回“暂时无法确认”；恢复验证则检查工具错误率和真实订单查询，而不是调低模型 token。

## Dashboard

### 质量

任务成功率、无答案率、人工修改率、引用支持率、安全违规。

### 可靠性

各模型/工具错误率、超时率、重试率、循环耗尽、checkpoint 恢复成功率。

### 性能与成本

首 token/P50/P95 总延迟、各阶段耗时、输入输出 token、单任务成本、缓存命中率。

注明延迟从何时计起、是否包含排队/审批、使用哪种分位数算法。分别展示“所有终态 run 的结束延迟”和“成功 run 的完成延迟”，同时保留超时、取消和仍在运行的数量；只看成功请求可能掩盖大量失败。手算见 [[06-评测安全生产/评测指标怎么算]]。

### 业务

工单处理时间、自动解决率、审批等待时间。技术指标必须能映射到真实业务结果。

## SLO 示例

以下为教学目标示例，需要结合真实业务设定统计窗口与分母：

- 99% 只读查询在 15 秒内得到结果或可解释失败。
- 100% 写工具都有审计与有效审批。
- 99.9% run 状态转换不丢失。
- 安全违规预算为 0。

第一条衡量“及时给出终态”，分母是窗口内服务已接收的只读查询；超时但仍未给出终态的请求不能消失。它不等于任务成功率：15 秒内快速失败也满足这条响应性目标，还必须搭配正确完成目标的质量指标。写工具的审批口径是“满足策略所要求的有效授权”，预授权的低风险动作不一定每次弹窗。第三条需要通过状态写入/恢复记录核对，不能只凭没有告警判断达标。

SLO 应区分模型慢、工具慢、排队与审批等待；否则一个总延迟无法指导优化。规定观察窗口结束时如何处理未完成请求，并对质量指标使用一致的 cohort（同一批已接收请求）。

## 过载时为什么要少接一点

假设服务可同时执行 8 个 run，等待队列最多 16 个；一次突发来了 30 个请求。演示策略是接收 8 个执行、16 个等待，其余 6 个立即返回“当前繁忙，可稍后重试”，并给出重试提示。这个限制叫**背压**：把容量不足及时传回上游，避免排队无限增长、所有请求一起超时。

这 6 个容量拒绝应单列，并进入“全部入口请求”的接纳率统计；已接收请求的任务成功率则另报，防止靠少接请求让成功率看起来更高。上述 8/16 只是算例，实际容量需测量模型和工具配额。

多租户场景可再设每租户同时运行上限，并轮流从各租户队列取任务，避免一个批量用户占满所有位置。过载时可优先保留交互查询、延后批量任务，或给出带时间戳的缓存结果；降级输出需明确能力或数据新鲜度变化，写操作仍遵守原有授权和幂等约束。

## 发布流程

1. 离线回归和安全测试。
2. 使用历史输入做 shadow run，不产生副作用。
3. 小比例 canary，绑定新控制面版本。
4. 比较质量、延迟、成本和失败分布。
5. 自动或人工决定扩大、暂停、回滚。

## Runbook

为模型不可用、工具错误率突增、成本异常、注入攻击和评测下降分别准备 runbook。Runbook 要包含检测信号、立即止损、降级行为、数据查询、负责人和恢复验证。

## 数据隐私

Debug 模式也不能无限记录原文。设计分级采样：普通成功只留元数据，失败留脱敏摘要，特定受控 run 经授权才保留完整内容；所有内容有过期和访问审计。
