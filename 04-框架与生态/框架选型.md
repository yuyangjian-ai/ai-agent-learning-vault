# 框架选型

## 先选问题，再选框架

- Java/Spring 团队，希望接入模型、工具、RAG：看 [[04-框架与生态/Spring AI 能力边界]]。
- 需要显式状态图、分支、检查点和复杂循环：看 [[04-框架与生态/LangGraph 概览]]。
- 希望工具/资源能被不同 AI 客户端统一发现和调用：看 [[04-框架与生态/MCP 概览]]。
- 简单模型调用或固定 Workflow：官方 SDK 加业务代码通常已经足够。

## 这些方案不在同一层

| 层次 | 代表方案 | 主要解决什么 |
| --- | --- | --- |
| 模型接入与开发抽象 | 官方 SDK、Spring AI | 消息、结构化输出、模型与向量库适配 |
| 运行编排 | 普通 Workflow、LangGraph | 节点、分支、循环、暂停和恢复 |
| 能力连接协议 | MCP | 让 Host 发现和调用外部工具/资源 |
| 业务 Runtime | 自己的服务代码 | 权限、审批、幂等、预算和审计 |

> [!example]- 帮助理解：它们可以组合，不是互相替代
> 一个 Java 客服系统可以用 Spring AI 接模型，用固定 Workflow 控制退款主路径，再通过 MCP Client 连接只读订单工具。无论选了哪些框架，业务服务仍要负责租户鉴权、退款审批和幂等。

## 评估维度

1. 状态与循环是否显式可控。
2. 工具、结构化输出、流式响应是否成熟。
3. 是否容易加入权限、审批和租户隔离。
4. trace 是否可导出，能否接入自己的评测。
5. 模型和向量库能否替换。
6. 团队是否能调试框架背后的原始请求与状态。

## 原则

框架是基础设施，不替你定义业务状态机、权限边界、评测标准和失败策略。学习阶段至少手写一次 [[02-核心机制/07-Agent Loop]]，再使用高级抽象。

## 一张更具体的选择表

| 需求 | 优先方案 | 原因 |
| --- | --- | --- |
| Java 服务接模型和 RAG | Spring AI / 官方 SDK | 与 Spring 生态和业务代码集成自然 |
| Python 中构建显式长运行状态图 | LangGraph | persistence、interrupt 和图编排是核心能力 |
| 向多个 AI Host 暴露统一工具 | MCP Server | 协议化发现与调用 |
| 三步固定数据处理 | 普通代码/Workflow | 框架收益小 |
| 单次抽取/分类 | 官方 SDK + schema | 不需要 Agent runtime |
| 高风险业务自动化 | Workflow + 局部 Agent + 审批 | 关键路径保持确定性 |

## 选型 PoC

不要用“Hello World”比较框架。选择一个真实但受控的垂直切片，至少包含：一次模型调用、一个只读工具、一个错误分支、一次状态保存和 trace。用相同任务比较代码透明度、测试难度、恢复能力、性能和团队理解成本。

## 锁定与退出成本

- Prompt、评测集和业务工具契约应尽量框架中立。
- 运行状态不要只以框架内部对象保存。
- Trace 导出到通用可观测平台。
- 关键工具本身作为普通服务测试。
- 记录哪些能力依赖特定框架，升级时针对它们回归。

## 选型反模式

- 因为演示代码短就认为适合生产。
- 用框架默认 Memory 替代业务状态。
- 为了 Multi-Agent 而选择复杂框架，但任务无法真正分解。
- 不锁版本，直接把网络示例复制进项目。
- 没有评测集就比较“回答感觉”。
