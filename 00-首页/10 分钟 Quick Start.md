# 10 分钟 Quick Start：用后端思维理解 AI Agent

适合 Node.js / TypeScript + Java 开发者。读完这页，你应该能解释 Agent 的运行方式、看懂一个最小实验，并知道哪些事不能交给模型决定。

**预计阅读 8–10 分钟。** 安装和动手运行另计；暂时不方便运行，直接看预期输出即可。不需要先学 Python，也不要求先装 Agent 框架。

## 0–2 分钟：Agent 是多了“模型决策”的业务程序

你熟悉的后端流程是：接收请求 → Service 执行业务 → 返回结果。Agent 让模型参与“下一步做什么”的选择，程序再检查并执行：

```text
用户给目标
  → 程序准备本轮材料
  → 模型提出动作或回复
  → 程序校验目标、参数、权限和预算
  → 执行工具，把结果交回模型，再决定下一步
  → 目标验收通过后完成；也可能暂停、拒绝或失败退出
```

这就是 **Agent Loop**。控制循环的代码叫 **Runtime**，可以先把它理解为你的应用 Service。

| 教程里的词 | 用熟悉的后端概念理解 |
| --- | --- |
| LLM（大语言模型） | 一个能理解文本、提出候选判断的外部服务；不是订单数据库 |
| Prompt + Schema | 任务说明 + 输出契约；类似明确的接口需求和 DTO 约束 |
| Tool（工具） | 暴露给模型申请调用的业务方法，例如只读查订单 |
| RAG（检索增强生成） | 先找相关文档，再把证据交给模型回答 |
| LLM Wiki | 让模型把资料整理成有来源、可维护的知识页面，供后续检索与复用 |
| Context / Memory | 本轮提供的材料 / 可供后续参考的记忆；都可能不完整或过期 |
| State（运行状态） | 程序保存的当前步骤、预算和待审批动作；不能只靠聊天记录 |

最重要的一句：**模型提出建议，程序掌握执行权。** 订单事实仍要查源系统，金额和权限仍由业务代码判断。

## 2–4 分钟：跟着一张“疑似重复扣款”工单走

用户说：“订单 ORD-001 好像扣了两次，帮我退掉多扣的一笔。”

1. **模型理解诉求**：这是支付问题，订单号是 ORD-001；“好像”只是待核实线索。
2. **程序核对身份与目标**：租户来自已验证的登录上下文；不能让模型填写，也不能偷偷换查另一张订单。
3. **工具查询事实**：读取支付状态、金额和已有退款记录。模型不能靠常识猜这笔钱发生了什么。
4. **RAG 查找规定**：找这笔业务适用的处理政策。历史订单可能适用旧版，不是一律选最新文档。
5. **业务规则与人工介入**：满足条件时生成具体处理建议和审批请求；模型不直接退款。
6. **准确汇报进度**：“已提交人工复核，尚未退款。”等待审批不是任务已经执行成功。

查政策和查支付不能互相替代：前者回答“规则是什么”，后者回答“这笔交易发生了什么”。引用能打开，也不代表原文支持回答。

如果主流程始终是这些步骤，用固定 **Workflow（工作流）** 就够了；只有下一步确实依赖新观察、需要动态选择时，才让模型在限定范围内决定。无需从多 Agent 开始。

## 4–7 分钟：看一圈可运行的 TypeScript 实验

仓库已提供缩小版：**只查询假订单状态，不包含支付、RAG 或退款。** 假模型按脚本提出动作，让你先看懂运行机制。

在仓库根目录执行以下命令；需要 Node.js 和 npm，具体环境准备见 [从这里开始](从这里开始.md)。首次安装需要联网，之后实验运行不联网、无需 API Key。

```powershell
npm --prefix labs/01-agent-runtime/typescript ci --ignore-scripts
npm --prefix labs/01-agent-runtime/typescript run start -- --scenario success
```

命令会自动编译。忽略 npm 的命令提示，关注输出中的这些字段（节选）：

```json
{
  "status": "completed",
  "simulated_usage": {
    "model_calls": 2,
    "tool_attempts": 1
  }
}
```

为什么查一次订单，却调用了两次模型？

- 第一次：模型提出 `get_order_status({order_id: "ORD-001"})`，此时还没有订单结果。
- 中间：Runtime 校验字段、任务目标和租户权限，工具才读取假订单。
- 第二次：模型看见工具返回的“待发货”等字段，形成回复；Runtime 验证它与观察一致后才完成。

这里使用固定回复模板校验，不是通用的自然语言事实核查。代码入口是 [runtime.ts](../labs/01-agent-runtime/typescript/src/runtime.ts) 的 `Runtime.run()`；完整说明见 [实验 README](../labs/01-agent-runtime/README.md)。

对 TypeScript：模型返回值先当作 `unknown`，校验后再使用，`as Decision` 不能代替检查。对 Java：反序列化成 DTO/record 后仍需校验；Runtime、模型适配器、工具分别对应应用 Service、外部服务接口、业务方法。两种语言的 [实现对照](../03-工程实践/TypeScript%20与%20Java%20实现对照.md) 可以之后再看，不必为了练习混合部署两套服务。

## 7–9 分钟：可靠性主要来自这五条约束

1. **格式、内容、权限分别校验。** JSON 合法不等于事实正确，也不等于允许执行；有权限读取的订单还必须是用户这次要查的订单。
2. **外部文字只是数据。** 工单、网页或工具结果中的“忽略之前规则”，不能变成系统指令；密钥也不能放进模型上下文或日志。
3. **循环必须能停。** 设置步数、时间和费用上限；证据不足就澄清或转人工，不能无限重试。每次运行保留步骤与实际工具结果，方便排错。
4. **取消和超时不是业务回滚。** 只读查询超时不能说“订单不存在”；写操作超时则可能已经生效，要先核对结果。重试同一笔写入需稳定的幂等键，避免重复生效。
5. **看回答，也看过程。** 答对了却越权，仍不算成功。假设 10 个应完成任务只有 8 个合格，成功率是 8/10；不能删掉两个超时后报 100%。

想观察失败，把成功命令最后的 `success` 换成 `unauthorized`：应看到 `status: denied`，工具执行次数为 0。演示命令的退出码可以是 0，要看 JSON 中的业务状态。

固定场景回归可以另行运行：

```powershell
npm --prefix labs/01-agent-runtime/typescript run evaluate
```

预期为 `total: 12, passed: 12, failed: 0`。这只证明 12 条公开合成场景的程序行为符合预期，**不代表真实模型准确率**；模拟 token 和耗时也不是真实费用、性能。接入真实模型后需要重新评测。

## 9–10 分钟：自测，然后选择下一步

**30 秒自测：** 模型返回了合法 JSON，支付查询超时，但 RAG 找到了退款政策。现在能说“已确认重复扣款并退款”吗？

> [!example]- 简短答案
> 不能。政策不能证明这笔支付事实，合法 JSON 也不授予退款权限。先有限重查或转人工，明确“尚未核实、尚未退款”；取得必要事实后再按规则进入相应审批。

读到这里，先记住：**让模型理解和建议，让工具提供事实，让程序控制执行，再用记录和评测验证结果。**

后续只选一个入口，不必一次读完：

- 想开始接真实模型：[项目 1：Minimal Chatbot](../05-项目实战/01-Minimal%20Chatbot.md)，先把一次调用、结构校验和失败处理做好。
- 想亲手写循环：[项目 2：Mini Agent CLI](../05-项目实战/02-Mini%20Agent%20CLI.md)，从只读工具起步。
- 想整理长期知识：先读 [RAG](../02-核心机制/05-RAG.md) 与 [Memory](../02-核心机制/06-Memory.md)，再读 [LLM Wiki](../02-核心机制/10-LLM%20Wiki.md)；可从 Markdown 与关键词搜索起步，无需向量数据库。
- 想系统学习：[8 周学习路线](学习路线.md)。先做基础版，再补 RAG、状态恢复、评测和生产专题。

Spring AI、LangGraph 和 MCP 可以等到遇见对应问题再学；它们不替你决定业务权限、审批和验收标准。
