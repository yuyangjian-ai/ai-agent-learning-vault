# 常见困惑与排错

这篇按“哪里卡住”查阅，不要求顺序读完。每个回答都指向已有章节。

## Prompt、RAG、微调，到底改哪个

| 真正的问题 | 优先做什么 | 例子 |
| --- | --- | --- |
| 任务或输出格式说不清 | Prompt、schema、边界样本 | “优先级高”没有定义 |
| 缺少实时业务事实 | 只读工具 | 订单此刻是否发货 |
| 缺少私有文档证据 | RAG | 公司售后政策第几条 |
| 需要稳定学习某种行为或风格 | 先建评测，再评估微调 | 大批有授权的标注样本呈现一致格式 |
| 步骤要跨工具和人工推进 | Runtime / Workflow | 查事实后生成预览并等待审批 |

微调是通过训练更新模型参数；RAG 是在本次输入中提供证据。更新频繁的订单和政策不适合靠记进权重来保持新鲜。微调也不会替代权限、工具和校验。先定位失败层，再选择改动。相关：[[01-基础/02-Prompt 与结构化输出]]、[[02-核心机制/05-RAG]]、[[03-工程实践/Workflow 与 Agent]]。

## LLM Wiki 能替代 RAG 吗

可以替代某些基础分块检索方案，但不能笼统说“替代 RAG”。LLM Wiki 先整理知识页面；如果回答时检索这些页面再生成，仍是广义 RAG。提前生成摘要也不是 Wiki 独有，GraphRAG 等方案同样会做。选择应看固定问题集上的证据覆盖、更新成本和错误情况，而不是只比较名称。见 [[02-核心机制/10-LLM Wiki]] 和 [[02-核心机制/05-RAG]]。

## 有了 LLM Wiki，还需要模型和向量库吗

生成式 LLM 负责自动归纳、更新页面及生成回答；Embedding 模型负责把文本变成向量；向量库负责找相似候选，三者职责不同。Wiki 可以从目录、链接和关键词搜索起步，按需要加入语义检索。省去 Embedding 和向量库，不等于省去生成式 LLM 或检索；写好了 Wiki 也不表示模型已经“学进权重”。见 [[01-基础/04-Embedding 与向量检索]]；可动手做 [[labs/02-llm-wiki/README|LLM Wiki 练习包]]。

## 上下文、Memory 和数据库有什么区别

上下文像这次开会桌上的材料；Memory 像下次开会可参考的笔记；数据库是订单等业务事实的记录系统。Wiki 页面可作为长期知识记忆的一种载体，数据库也可用来存 Memory，区别在职责而非文件格式。桌上材料要筛选，笔记可能过期，付款状态要回源系统查询。摘要压缩了材料，却不保证保留所有细节。见 [[02-核心机制/06-Memory]] 和 [[03-工程实践/Context Engineering]]。

## Agent、Workflow、框架和 MCP 怎样分工

Workflow 固定主要路径；Agent 在约束内选择下一步；框架帮助实现模型调用或状态编排；MCP 统一连接外部能力的方式。它们可以组合。判断是否需要自由规划时，问“下一步是否必须根据刚获得的证据才能决定”。见 [[04-框架与生态/框架选型]]。

## 模型“知道工具”却不调用怎么办

先检查本轮是否真的发送了该工具定义、接口与模型是否支持、描述是否明确、调用是否被策略过滤，再看模型是否有足够参数。模型没有订单号时，正确行为可能是先询问。不要通过开放全部工具来修一个选择错误。见 [[02-核心机制/04-Tool Calling]]。

## 为什么温度设为 0 仍不能代替测试

采样设置只是影响输出的一项因素，模型版本、上下文、工具返回、服务实现也会影响结果。确定性校验放程序中；固定输入重复运行是评估稳定性的手段，但不等于增加了独立的业务样本。见 [[01-基础/01-LLM 基础]] 和 [[06-评测安全生产/评测指标怎么算]]。

## 相似度最高、引用能打开，答案就可靠了吗

相似度用于排序；能打开的引用只证明资源存在。还要检查权限、适用版本、原文是否支持结论，以及关键断言是否漏引。例如原文说“通常 3–5 天”，回答“保证 3 天”仍然不忠实。见 [[01-基础/04-Embedding 与向量检索]]、[[06-评测安全生产/Agent 评测]]。

## 多加几个 Agent 会更聪明吗

可能扩大可处理的上下文，也可能重复错误并增加合并成本。先用相同任务比较单 Agent 和多 Agent，记录总费用、耗时、证据质量和冲突。多个人同意不能代替证据，关键路径也不会因为并行而消失。见 [[02-核心机制/09-Multi-Agent]]。

## 工具超时、任务取消、动作失败是一回事吗

不是同一种状态。超时表示没在期限内拿到结果；取消表示要求停止；失败需要明确的失败证据。已经发送的邮件不会因客户端断线而收回。查执行结果、保留关联 ID，才能决定下一步。见 [[03-工程实践/异步任务与取消]] 和 [[03-工程实践/错误恢复与幂等]]。

## 怎样避免“好像优化了”

先保存基线，每次只改变一个主要变量；在同一批固定样本上比较端到端成功、安全、延迟与成本。格式通过率提高、答案更流畅、均值变快，都可能掩盖某类严重失败。计算方法见 [[06-评测安全生产/评测指标怎么算]]。

## 最后如何排一个真实失败

按顺序问：输入契约对吗 → 身份和范围对吗 → 证据找对了吗 → 工具执行结果是什么 → 状态是否正确推进 → 最终回答是否忠实 → 指标分母是否包含这次失败。

> [!example]- 示例：答案说“已退款”，工具其实只创建了审批
> 根因优先定位到结果解释/状态映射。把 `APPROVAL_CREATED` 与 `REFUND_COMPLETED` 分开，并新增“审批创建成功但未执行退款”的评测样本。无须先换模型或扩充向量库。
