# 模型网关与路由

## Model Gateway 的职责

Model Gateway 不是一个简单 HTTP 代理。它统一处理模型身份、能力声明、限流、超时、错误、usage、trace、凭据、内容策略和供应商差异。

## 能力声明

每个部署配置显式声明：是否支持工具调用、并行工具、原生结构化输出、视觉输入、最大上下文、流式事件和数据区域。路由器按任务需要选择，不能假设所有模型行为相同。

## 路由策略

- 固定路由：一个任务绑定一个经过评测的模型，最容易复现。
- 能力路由：只有需要视觉或大上下文时切换特定模型。
- 质量/成本路由：小模型先处理，低置信或失败再升级。
- 合规路由：敏感任务只能进入指定区域或私有部署。

> [!example]- 帮助理解：先满足硬约束，再优化价格
> 假设任务要求“中国区域、支持工具调用、原生结构化输出、上下文至少 32k”。路由器先淘汰不满足任一硬约束的模型，再在剩余候选中比较固定评测集质量、P95 和成本。
>
> ```yaml
> routeDecision:
>   task: ticket-classification
>   rejected: {model-A: wrong-region, model-B: no-tool-calling}
>   selected: logical-small-v3
>   actualProviderVersion: provider-model-2026-08
>   policyVersion: route-v5
> ```
> Fallback 也必须重新通过所有硬约束，不能因主模型故障就把敏感数据路由到不合规区域。

## Fallback 的陷阱

备用模型的 tokenizer、工具支持、schema 严格度和安全策略可能不同。只有在同一评测集上验证过的模型组合才能自动 fallback；否则应返回可解释失败。

## 版本固定

线上 run 保存逻辑模型名和实际提供商版本。Prompt、schema、模型、路由策略任何一个变化都可能改变行为，发布时应作为一个整体评测。

## 成本治理

在调用前估算最大成本，在流式或循环中累计实际 usage。按用户、租户、任务和模型设置配额。成本异常往往来自上下文重复、工具大结果、重试叠加和无效循环，而不只是模型单价。

## 练习

设计一个“工单分类用小模型，复杂解释用大模型”的路由器。定义升级条件、fallback 条件，以及如何验证小模型没有把高风险工单错误拦截。

> [!example]- 示例答案（参考）
> - 默认小模型输出 `category/confidence/riskSignals/evidence`。
> - 升级条件：`confidence < 0.8`、多标签冲突、涉及支付/隐私/法律、证据字段为空或业务规则校验失败。
> - Fallback：小模型超时可重试一次或切到已通过同一评测集的大模型；大模型不可用时，高风险工单直接转人工，不能降级为猜测。
> - 验证：构造足量高风险和伪装成普通问题的样本，把“高风险被小模型判为普通且未升级”设为关键漏检指标，发布门禁要求该数量为 0。
