# 状态、事件与持久化

## 为什么 Agent 需要显式状态

多步任务可能等待工具、用户输入或审批，也可能在进程重启后恢复。只把对话消息放在内存里，会导致无法判断哪一步已完成、哪些副作用发生过、预算用了多少。

## 状态与事件

- 状态回答“现在是什么情况”。
- 事件回答“发生了什么导致状态改变”。

```text
Event: ToolCallRequested(step=3, tool=send_email)
Event: ApprovalRequested(actionHash=abc)
Event: ApprovalGranted(by=user-1)
Event: ToolExecutionSucceeded(messageId=mail-9)

State: status=COMPLETED, stepCount=3, lastMessageId=mail-9
```

事件应追加而不是覆盖，状态可以由事件增量归并并定期做 snapshot。

> [!example]- 帮助理解：Command、Event 和 State 不要混淆
> | 类型 | 周报场景中的例子 | 表达的含义 |
> | --- | --- | --- |
> | Command | `SendWeeklyReport(reportId=R7)` | 希望系统执行什么，可能被拒绝或失败 |
> | Event | `SendStarted`、`SendSucceeded` | 已经发生了什么，不应被改写 |
> | State | `status=SENT, messageId=M9` | 归并历史事件后当前是什么情况 |
>
> “请求过发送”不等于“已经发送”，发送接口超时也不等于 `SendFailed`。如果外部结果未知，应记录 `SendOutcomeUnknown`，恢复后再按幂等键查询。

## 乐观并发控制

同一个 run 可能同时收到工具回调、用户取消和超时事件。更新时使用 `stateVersion`：只有数据库版本仍等于读取版本时才提交，否则重新读取并判断事件是否仍适用。

## Checkpoint

在模型决策后、执行副作用前，先持久化“准备执行的动作”；执行成功后再记录结果。这样崩溃恢复时可以查询幂等键，而不是猜测动作是否发生。

一个 checkpoint 至少包含：状态版本、当前节点、消息/证据引用、待处理动作、已消耗预算、deadline 和控制面版本。

## 数据保留

运行轨迹有调试价值，也可能包含敏感信息。按数据类型设置不同保留期：审计事件可能长期保留，完整 Prompt 和工具结果应更短并脱敏；删除用户数据时要处理派生摘要、向量和缓存。

## 回放

回放分两种：

- 纯回放：使用历史模型/工具结果重建状态，不产生外部副作用。
- 重新执行：用新版本从某个 checkpoint 分叉，所有写工具必须进入模拟环境或重新审批。

## 练习

为“生成并发送周报”的 Agent 列出事件序列。假设发送接口超时后进程崩溃，说明恢复时怎样避免重复发邮件。

> [!example]- 示例答案（参考）
> 事件序列：`RunCreated → DataCollected → DraftGenerated → DraftValidated → ApprovalRequested → ApprovalGranted → SendPrepared(idempotencyKey=weekly-2026-W29-teamA) → SendStarted → SendOutcomeUnknown`。
>
> 恢复后读取 checkpoint 和幂等键，先调用邮件系统查询发送结果：若已存在 message ID，则追加 `SendSucceeded`；若明确未发送，再用同一幂等键重试；若无法确认，则进入人工处理，不能直接生成新键重发。
