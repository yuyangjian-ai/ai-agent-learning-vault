# 项目实战总览

默认以 Node.js + TypeScript 实现四个项目；也可以全程使用 Java。先用熟悉的业务分层和原生 SDK，不要求先学 Python。两种语言的职责映射与短例子见 [[03-工程实践/TypeScript 与 Java 实现对照]]。

先选一个你现在能完成的级别。**基础通过**允许离线 mock（按脚本返回结果的假模型/假服务）；**标准完成**接入真实模型 API 并完成固定样本评测；**生产加餐**才讨论真实业务流量、容量和上线运维。各章后续架构和完整清单以“标准完成”为目标。

> [!important] 所有级别共同的门禁
> 权限、输入校验、有限循环/重试、敏感信息保护和失败退出从基础版开始就要实现。只在固定测试集上没有发现违规，不等于生产安全已经得到证明。mock 输出必须标为模拟；不能用它的脚本命中率宣称模型准确率，也不能把本地耗时当作真实 API 延迟。

标准完成的参考投入分别为 2–3 天、1–2 周、1–2 周、2–4 周；基础版通常更小，生产加餐取决于真实数据和运行环境，不承诺固定工期。每章的教学数值门禁应在评测前固定，不能看到结果后降低门槛。

**项目 3 可选扩展：LLM Wiki。** 学完 [[02-核心机制/05-RAG]]、[[02-核心机制/06-Memory]] 后，阅读 [[02-核心机制/10-LLM Wiki]]，完成 [[labs/02-llm-wiki/README|Wiki 文件练习]]。练习从目录与关键词检索起步，比较直接查原文与先查整理页面；保留来源、处理冲突并验证失效传播。它不要求 Embedding 模型或向量数据库，也不取代项目 3 的检索与引用验收。

## 第一个小时怎么开始

没有 API 密钥时，可以先跑 [[labs/01-agent-runtime/README|离线 Agent Runtime 实验]]，观察“模型建议调用 → 程序校验 → 工具结果 → 停止”的过程。在仓库根目录运行：

```powershell
npm --prefix labs/01-agent-runtime/typescript ci --ignore-scripts
npm --prefix labs/01-agent-runtime/typescript run start -- --scenario success
npm --prefix labs/01-agent-runtime/typescript run evaluate
```

它使用模拟模型决策和本地样例，不消耗模型 API 费用，适合理解运行机制；首次安装编译依赖需要联网，运行本身离线。它不替代项目中的真实 API 质量评测。

## 每个项目都要交付

- README：目标、范围、启动方式和限制。
- 架构图：组件、数据流、权限边界。
- 测试/评测：正常、边界、失败和攻击样本。
- 运行轨迹：模型版本、Prompt 版本、工具调用、耗时和成本。
- 复盘：最严重的失败、根因、下一版改动。

使用 [[99-模板/项目实验模板]] 记录每次实验；最终把失败样本加入 [[06-评测安全生产/Agent 评测|评测集]]。

工单分类统一引用 [[01-基础/02-Prompt 与结构化输出#工单分类契约]]。报告比例时同时写分子/分母和统计单位，例如 `54/60 次运行正确`；重复跑 20 条输入 3 次仍然只有 20 条不同输入，不是 60 条独立业务样本。质量主指标以全部输入/运行计数，解析失败、拒绝执行和超时不能悄悄从分母剔除；安全测试则按预设拒绝行为评分。

## 综合项目

完成前三个项目的基础或标准级别后，进入 [[05-项目实战/04-客服工单 Agent]] 的对应级别。它把分类、RAG、工具、Workflow、审批和评测组合成受控业务流程；无需为了完成学习，提前连接生产工单或真实支付系统。

## 项目不是功能清单

每次迭代只改变一个主要变量，并保留基线。比如优化 RAG 时，固定模型和生成 Prompt，只比较切分或检索；优化 Agent Loop 时，固定工具契约，只比较终止和恢复策略。

## 证据包

每个项目最后生成一个 evidence pack：

- 架构和威胁模型
- 版本清单
- 评测数据集与结果
- 3–5 个典型失败 trace
- 成本与延迟报告
- 已知限制和下一步

这比“演示一次成功流程”更能说明你真正掌握了 Agent 工程。

> [!example]- 帮助理解：一个最小 evidence pack
> ```text
> evidence-pack/
>   manifest.yaml
>   eval-baseline.json
>   eval-candidate.json
>   traces/failure-001.json
>   cost-report.md
>   known-limitations.md
> ```
> `failure-001` 通过 run ID 进入评测数据集；修复后使用同一个 eval version 比较 baseline 与 candidate。这样架构、失败轨迹、评测结果和版本变更能形成同一条证据链，而不是几份互不关联的文档。
