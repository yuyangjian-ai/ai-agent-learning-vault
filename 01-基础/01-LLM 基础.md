# LLM 基础

## 一句话定义

大语言模型根据已有上下文预测后续 token。它擅长从模式中生成结果，但并不天然拥有事实数据库、长期记忆或执行权限。

## 必须掌握的四件事

1. **Token**：模型处理文本的基本单位；输入和输出都会占用预算。
2. **上下文窗口**：单次调用能看到的信息上限，不等于永久记忆。
3. **采样参数**：temperature 等参数影响输出的随机性，但不能修复缺失知识。
4. **幻觉**：模型可能生成形式可信但事实错误的内容，因为目标是生成合理序列，不是验证真伪。

## 工程类比

把 LLM 看成一个能力很强但不稳定的纯函数：

```text
输出 = model(模型版本, 消息, 工具定义, 参数)
```

它的返回值需要验证；重要事实需要检索或工具支撑；高风险动作需要权限和确认。

## 常见误区

- “上下文越长越好”：噪声会稀释关键信息，并增加延迟和成本。
- “低 temperature 就不会错”：它只降低随机性，不保证事实正确。
- “模型知道当前数据库内容”：除非通过 [[02-核心机制/04-Tool Calling]] 或 [[02-核心机制/05-RAG]] 提供。

## 一次生成到底发生了什么

下面是一张有意简化的链路图。学习 Agent 时，不需要先掌握完整的深度学习数学，但要知道每一层可能带来什么工程影响。

```mermaid
flowchart LR
    Text["输入文本"] --> Tokenizer["Tokenizer"]
    Tokenizer --> IDs["Token IDs"]
    IDs --> Model["Transformer 推理"]
    Model --> Distribution["下一个 token 的概率分布"]
    Distribution --> Sampler["采样策略"]
    Sampler --> Next["选出下一个 token"]
    Next --> Model
```

模型每次只预测“下一个 token”，不断重复后形成一段回答。因此：

- 它可以生成非常流畅的长文本，但流畅不等于正确。
- 同一个输入可能产生不同输出，尤其是在采样较随机时。
- 前面生成的错误会进入后续上下文，形成连锁偏差。
- 模型并不是先在内部完成一篇答案再逐字打印出来。

## 重要参数怎么理解

| 参数 | 作用 | 常见误区 |
| --- | --- | --- |
| temperature | 调整概率分布的平滑程度 | 设为 0 也不代表绝对确定或正确 |
| top_p | 只从累计概率达到阈值的候选中采样 | 不应同时频繁调 temperature 和 top_p |
| max output tokens | 限制最大输出长度 | 太小会截断 JSON 或工具参数 |
| stop | 遇到特定序列停止 | 可能与用户内容意外冲突 |
| seed | 某些 API 提供的近似复现参数 | 模型后端变化后未必完全一致 |

对分类、抽取、工具参数生成等任务，通常希望输出更稳定；对头脑风暴和文案变体，可以允许更高随机性。参数选择必须通过样本评测，而不是背一个“最佳值”。

## 能力边界：知道、推断、行动

把模型能力拆成三层更容易设计系统：

1. **参数知识**：训练时学到的通用模式，可能过时，也无法追溯来源。
2. **上下文推断**：根据当前输入完成分类、总结、比较、生成等任务。
3. **外部行动**：读取数据库、搜索文件、发消息等，必须由工具执行。

当问题需要当前价格、用户真实权限、订单状态时，答案必须来自第三层的源系统；当问题只需要把已提供文本改写为固定格式时，第二层通常足够。

## 幻觉的四种常见来源

| 来源 | 例子 | 处理方式 |
| --- | --- | --- |
| 知识缺失 | 编造一个不存在的 API 参数 | RAG、工具查询、允许拒答 |
| 指令模糊 | “帮我处理这个问题”没有完成标准 | 明确任务契约与 schema |
| 上下文冲突 | 系统规则与检索文档互相矛盾 | 标明优先级、隔离不可信内容 |
| 生成链偏移 | 早期误判导致后面推理都偏离 | 分步验证、关键事实用工具检查 |

## 模型选型不只看排行榜

为具体任务比较：质量、上下文容量、结构化输出/工具支持、延迟、价格、数据合规、可用区域和稳定性。一个较小模型如果在固定任务上通过评测，通常比盲目使用最大模型更经济。

### 最小选型实验

1. 准备 30–100 条能代表真实分布的样本。
2. 定义必须满足和绝对禁止的行为。
3. 用完全相同的 Prompt、schema 和工具比较候选模型。
4. 同时记录正确率、P95 延迟、成本与失败类型。
5. 把模型版本作为系统版本的一部分固定下来。

## 练习

1. 找一个模型容易“自信编造”的问题，设计三种处理：允许拒答、RAG 提供证据、工具查询源系统。
2. 用同一输入分别测试低/中/高随机性，观察哪些字段发生变化。
3. 解释为什么“让模型认真一点”不如加入可验证的证据和验收标准。
